
Исходные рыночные данные: требования и решения
==============================================


Назначение документа
--------------------

Зафиксировать изученные материалы касательно источников свежих рыночных данных и принятые решения по поводу исследовательской стратегии и будущего перехода к получению актуальных данных и размещению тестовых и реальных ордеров на бирже.


Краткое резюме текущих решений
------------------------------

При поиске и выборе исходных данных важно учитывать, что целью FMD-проекта является выявление закономерностей изменения рыночных цен, связанных с психологией участников, повторяющимися внутридневными и календарными событиями, а также механизмами функционирования и регулирования рынка. Ожидается, что подобные явления неоднократно проявляются в пределах одного торгового дня. А значит, для обучения модели нужны выборки данных периодом от недели (минимально) и более (месяц - оптимально, год - идеально).
Следовательно, для исследования нужны данные о фактически совершённых сделках на регулируемых организованных торговых площадках с централизованным исполнением заявок, где в дальнейшем планируется реальная торговля.

Примечание: под психологией понимается поведение трейдеров в зависимости от новостей и динамики рынка. К повторяющимся событиям относятся, например, открытие и закрытие торгов, публикация новостей, внутридневные перерывы, периоды планового обслуживания, перераспределения, синхронизации, репликации и т.п. Рыночные механизмы - алгоритмы, выполняющие рыночные рутинные задачи (осуществление сделок, коррекции, балансировки и т.п.).

Для исследования подходят данные по финансовым инструментам, если:

- инструмент торгуется на регулируемой централизованной бирже;
- по нему совершаются реальные зарегистрированные сделки;
- инструмент обладает достаточной ликвидностью;
- период не менее недели (желательно непрерывный);
- данные содержат зарегистрированные площадкой цены и объемы сделок;
- данные не рассчитываются и не формируются брокером.

Подходящие классы:

* акции компаний - цена формируется реальными заявками покупателей и продавцов;
* биржевые фонды (ETF) - реальные биржевые инструменты;
* биржевые фьючерсы - наиболее ликвидные валютные, индексные, товарные, процентные и энергетические контракты.

Не подходят:

* CFD;
* брокерские валютные котировки;
* внебиржевой Forex;
* варранты и сертификаты, цену которых поддерживает эмитент;
* сами расчетные индексы;
* синтетические и сгенерированные сторонние данные;
* малоликвидные инструменты (акции, облигации, опционы и контракты).

Примечание: допускаются только синтетические данные собственного производства (sci-synthgen), параметры генерации которых полностью известны. Они предназначены не для имитации рынка, а для проверки работы самообучающегося модуля распознавания и прогнозирования.

Дополнительные требования к исходным рыночным данным:

- приемлемые форматы данных:
    * тики - упорядоченный поток событий, из которого можно однозначно выделить совершенные сделки и определить для каждой сделки инструмент, время, цену и объем;
    * готовые стандартные OHLCV-свечи с интервалом 1 секунда;
- период данных - 2010 год или позднее;
- глубина истории - не менее одной недели.

Котировки bid/ask без данных о фактически совершенных сделках не считаются достаточными.

Такие данные позволят проверить гипотезу о возможности прогнозирования (PoC). Очевидно, реальную торговую модель следует обучать на свежих данных целевой площадки.

Регламент принятия исходных данных
----------------------------------

Поскольку данные приходят из множества источников в разных форматах, требуется предварительная нормализация. Для каждого источника создаётся отдельный нормализатор. Он распаковывает и считывает исходные файлы, приводит пригодные записи к единому внутреннему CSV-формату, отбрасывает ненужные и невалидные записи, сортирует результат по времени и сохраняет один файл результата обработки источника за исходную дату: `data/normalized/<source>/YYYYMMDD.csv`.

Внутренний формат и критерии фильтрации следует указать в основной документации (`docs/SPECIFICATION.md`).
Наличие нормализованного файла за некоторую дату является свидетельством произведенной нормализации, поэтому дополнительной фиксации в документации или реестре не требуется.
После успешной нормализации исходные файлы удаляются из проекта. При необходимости их внешний архив ведётся отдельно.
Поскольку новые исходные данные будут поступать ежедневно, следует предусмотреть пакетную обработку, при которой для каждого источника запускается свой нормализатор.


Realtime-данные и торговый брокер
---------------------------------

Для получения рыночных данных в реальном времени через API рассматриваются такие варианты:

1. Interactive Brokers (IBKR)

    * Windows 11: да — Trader Workstation (TWS); Windows 11 официально рекомендован.
    * Web: да — Client Portal, торговля через браузер.
    * Android: да — IBKR Mobile.
    * Python API: да — официальный TWS API для Python.
    * REST API: да — Web API.
    * WebSocket: да.
    * Realtime market data через API: да, при наличии подписки на соответствующую биржу.
    * Несколько бирж: да, более 170 рынков в 40 странах.
    * Ручные ордера: Windows / Web / Android.
    * Примечание: технически очень подходящий вариант.

2. Saxo

    * Windows 11: да — SaxoTrader Desktop; поддерживается Windows 10+.
    * Web: да — SaxoTrader работает непосредственно в браузере.
    * Android: да — официальное Android-приложение SaxoTrader.
    * Python API: отдельной «Python-библиотеки» уровня IBKR нет, но Python нормально работает через OpenAPI.
    * REST API: да.
    * WebSocket: да, для streaming data.
    * Realtime market data через API: да, с соответствующими market-data permissions.
    * Несколько бирж: да.
    * Ручные ордера: Windows / Web / Android.
    * Примечание: IBKR сильнее как программируемая инфраструктура - есть официальный Python/TWS API и хорошая документация для алгоритмической работы.

Среди немецких брокеров для ручного размещения ордеров с автоматическим удержанием и перечислением немецких налогов, предоставляющих торговые веб- и андроид-терминалы, наиболее перспективные: flatex, comdirect и Consorsbank. Исключены сервисы, ориентированные на отдельные классы инструментов, не подходящие для ручной торговли или автоматического учета немецких налогов.

ВАЖНО: не обязательно получать рыночные данные с того же брокера, через которого осуществляется размещение ордеров.
Главное, чтобы исходный поток данных был актуальным и поступал с приемлемой задержкой. Например, данные можно получать и обрабатывать через API IBKR, а ордера размещать через flatex или comdirect. То есть, система может работать в двух независимых контурах:

1) Market Data Provider > Converter > Predictor > Explorer (отображение курса и аналитики)
2) Explorer > Принятие решения > Trading Broker > Размещение ордера

Позже, когда эффективность торговой схемы будет подтверждена, можно будет добавить автотрейдер, принимающий решения по выбранной стратегии и риск-менеджменту и автоматически размещающий ордера (например, через IBKR) и цикл замкнется: получение данных > анализ и принятие решения > размещение ордера.


План развития проекта
---------------------

1) 1 поток > ручная торговля > накопление статистики > проверка устойчивости
2) автоматизация одного потока, создание автотрейдера
3) масштабирование автотрейдера на N потоков/инструментов


Приоритетные рынки и инструменты
--------------------------------

Крутые мамкины трейдеры торгуют в основном самыми ликвидными активами:

| Что                                       | Почему                                               |
| ----------------------------------------- | ---------------------------------------------------- |
| Фьючерсы на индексы: S&P 500, Nasdaq, DAX | Большой поток сделок, узкие спреды, легко Long/Short |
| Биржевые валютные фьючерсы                | Огромная ликвидность                                 |
| Ликвидные акции США                       | Apple, Nvidia, Microsoft и т.п.                      |
| Нефть, золото, облигации - через фьючерсы | Ликвидно, но больше внешних факторов                 |


Справочная информация
---------------------

Приблизительное количество свечей для рынка с 23-часовой сессией:

| Масштаб | Свечей за сессию |
| ------: | ---------------: |
|     1 s |           82 800 |
|     5 s |           16 560 |
|    10 s |            8 280 |
|    15 s |            5 520 |
|    30 s |            2 760 |
|    60 s |            1 380 |

Ожидаемые поля данных японской свечи (OHLCV):

| Поле                     | Смысл                                                      |
| ------------------------ | ---------------------------------------------------------- |
| `symbol`                 | конкретный контракт, например `CLZ26`, а не просто «нефть» |
| `time_start`, `time_end` | границы интервала                                          |
| `open`                   | цена первой сделки                                         |
| `high`, `low`            | максимум и минимум сделок                                  |
| `close`                  | цена последней сделки                                      |
| `volume`                 | суммарный объем сделок (в заданных единицах)               |


Примечание: для прогнозирующей модели FMD-системы точная привязка данных к календарной дате не важна, т.к. модель работает с хронологическим потоком свечей заданного инструмента, анализирует их относительные изменения и даёт относительный прогноз (дерево вероятностей). Как следствие, в данных для обучения модели могут быть пропущены какие-то дни - это не критично.

Примечание: для исследования и последующей работы применяются стандартные японские свечи (OHLCV).
